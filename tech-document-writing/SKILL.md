# Tech Document Writing

このスキルは、日本語の技術ブログや技術解説を書くときに使用する。

主な対象は次のとおり。

- 技術ブログ
- 技術解説記事
- 技術紹介
- アーキテクチャ解説
- 仕組みの説明
- 技術比較
- 調査結果のまとめ
- 技術選定の解説
- 問題分析
- 実験・検証結果の解説

操作手順や運用手順を主目的とする文書は対象外とする。

# 目的

技術文書では、単に情報を列挙するのではなく、読者が次を理解できることを目指す。

- 何について説明しているのか
- なぜその技術や問題が重要なのか
- どのような仕組みなのか
- なぜそのような挙動になるのか
- 他の方法と何が違うのか
- どのような利点と制約があるのか
- どのような場面で使うべきなのか

「何をすればよいか」だけではなく、「なぜそうなるのか」を重視する。

# 想定読者を定める

記事を書く前に、想定する読者の知識レベルを考える。

例えば次のように区別する。

- 技術自体を初めて知る人
- 周辺技術は知っているが対象技術は知らない人
- 実際に利用している開発者
- 内部実装まで知りたい開発者

説明する内容と省略する内容は、想定読者に合わせる。

専門用語を避けることを目的にしない。

必要な専門用語は使用し、読者が知らない可能性があるものだけ補足する。

# 最初に「何の話か」を明確にする

記事の冒頭では、テーマを早い段階で明らかにする。

長い背景説明から始めて、何を説明する記事なのか分からない状態を作らない。

例えば次のように始める。

```text
llama.cpp では、複数の GPU にモデルを分割してロードできます。

ただし、2 枚の GPU の VRAM が単純に 1 つの巨大な VRAM として扱われるわけではありません。
この記事では、llama.cpp のマルチ GPU 推論でモデルがどのように配置されるのかを整理します。
```

読者が記事を読むべきか早い段階で判断できるようにする。

# 結論を隠さない

重要な結論を記事の最後まで意図的に隠さない。

技術解説では、必要に応じて最初に概要や結論を示し、その後で理由を説明する。

例えば:

```text
結論から言えば、CPU オフロードは VRAM 使用量を減らせますが、
GPU と CPU の間でモデルを移動するため、推論速度とのトレードオフがあります。
```

その後で、

- 何が GPU に置かれるのか
- 何が CPU に置かれるのか
- なぜ VRAM が減るのか
- なぜ遅くなるのか

を順に説明する。

# 背景から仕組みへつなげる

技術を説明するときは、背景知識だけを長々と説明しない。

背景は、その後の仕組みを理解するために必要な範囲に限定する。

推奨する流れ:

```text
問題・疑問
↓
前提となる知識
↓
仕組み
↓
具体例
↓
結果・性質
↓
メリットと制約
```

例えば GPU メモリ不足について説明するなら、

```text
なぜ OOM が起きるのか
↓
モデルがどのように VRAM を使用するのか
↓
CPU オフロードでは何が変わるのか
↓
VRAM と速度がどう変化するのか
```

のようにつなげる。

# 「なぜ」を説明する

技術解説では結果だけを書かない。

悪い例:

```text
CPU オフロードを有効にすると遅くなります。
```

よりも:

```text
CPU オフロードでは、モデルの一部を必要に応じて CPU メモリと GPU メモリの間で転送します。

そのため VRAM 使用量を抑えられる一方、PCIe などを経由したデータ転送が追加され、GPU のみで処理する場合より推論時間が長くなります。
```

のように、因果関係を示す。

# 因果関係を飛ばさない

技術者には自明に見える途中の論理でも、記事のテーマに重要なら省略しない。

例えば:

```text
VRAM が足りない
↓
CPU オフロードを使う
↓
動く
```

だけではなく、

```text
モデル全体を GPU に配置すると VRAM に収まらない
↓
モデルの一部を CPU メモリに保持する
↓
同時に GPU 上へ配置するデータ量が減る
↓
必要な VRAM が減る
↓
16 GB の GPU でも実行できる可能性が生まれる
```

と説明すると理解しやすい。

# 抽象と具体を往復する

抽象的な説明だけを続けない。

概念を説明した後には、具体例を入れる。

例えば:

```text
DI コンテナは、オブジェクト間の依存関係を外部から組み立てます。
```

だけで終わらず、

```java
class UserService {
    UserService(UserRepository repository) {
        this.repository = repository;
    }
}
```

のような例を示し、

```text
この例では `UserService` 自身が `UserRepository` を生成せず、外部から受け取っています。
DI コンテナは、この「外部から渡す」部分を担当します。
```

と説明する。

コードを掲載すること自体を目的にしない。

コード例が何を示しているのかを本文で説明する。

# 具体例は小さくする

概念説明用のコード例は、説明対象に必要な部分だけを残す。

例えば DI を説明するために、

- Web API
- データベース設定
- ロギング
- エラー処理
- DTO

まで含める必要はない。

実際のプロジェクト全体を再現するより、説明している概念が見えることを優先する。

# コードの前後を文章でつなぐ

コードブロックだけを連続して置かない。

コードの前では、

- 何を見るコードなのか
- 何に注目するのか

を書く。

コードの後では、

- 何が起きているのか
- どこが重要なのか

を書く。

例えば:

```text
まず、`UserService` が依存オブジェクトを自分で生成する例を見ます。
```

```java
class UserService {
    private final UserRepository repository = new UserRepository();
}
```

```text
この実装では `UserService` が `UserRepository` の生成方法まで知っています。
そのため、両者の結合が強くなります。
```

コードを読者に丸投げしない。

# 図が適しているものは図で説明する

次のようなものは、文章だけより図が適している場合がある。

- データフロー
- リクエストフロー
- コンポーネント間の関係
- 認証フロー
- ネットワーク構成
- 状態遷移
- シーケンス
- 階層構造

文章で無理に位置関係や流れを表現しない。

ただし、図だけを置いて説明を終えない。

図を見るべきポイントを本文でも説明する。

# 比較では比較軸を揃える

複数の技術を比較するときは、同じ観点で比較する。

例えば:

```text
- 実行モデル
- 拡張性
- メモリ使用量
- 性能
- 導入コスト
- 運用上の制約
```

などの比較軸を決める。

一方の技術では性能を説明し、もう一方では使いやすさだけを説明するような非対称な比較を避ける。

# 優劣ではなくトレードオフを書く

技術比較では、単純に「A の方が優れている」と結論付けない。

可能な限り、

```text
A は X に強いが Y が弱い。
B は Y に強いが X では不利になる。
```

という形で整理する。

選択が利用条件によって変わる場合、その条件を示す。

例えば:

```text
VRAM を節約することが最優先なら CPU オフロードが有効です。

一方、十分な VRAM があり推論速度を優先する場合は、モデル全体を GPU に置く方が適しています。
```

# 用語の粒度を揃える

異なる抽象度の概念を同列に扱わない。

例えば:

```text
Java
Spring Boot
Docker
REST API
```

は、それぞれ言語、フレームワーク、コンテナ技術、アーキテクチャスタイルであり、同じカテゴリではない。

比較や列挙では、何の分類なのかを明確にする。

# 用語は最初の登場時に整理する

略語や固有用語が重要な場合は、最初に簡潔に説明する。

例えば:

```text
VRAM（Video RAM）は、GPU が直接利用するメモリです。
```

以降は `VRAM` とだけ記載してよい。

一般的な読者が十分知っている用語まで毎回定義しない。

# 同じ概念には同じ名前を使う

途中で呼び方を変えない。

例えば同じ対象を、

- CPU オフロード
- CPU 退避
- CPU 転送
- CPU 配置

と理由なく切り替えない。

異なる概念の場合だけ用語を分ける。

# 事実と解釈を区別する

次を混同しない。

- 仕様として確認できること
- 実験結果
- ログから確認できること
- 推測
- 解釈
- 筆者の推奨

例えば:

```text
ログでは `n_decoded = 203872` と記録されています。
```

は観測事実。

```text
長大な出力生成によって処理時間が延びた可能性があります。
```

は解釈。

同じ確度で書かない。

# 不確かな情報を断定しない

確認できていない内部実装について、

```text
内部では必ず X を行っています。
```

と書かない。

必要に応じて、

```text
実装を見る限りでは
```

```text
この挙動からは
```

```text
〜と考えられます
```

など、情報の確度が伝わる表現を使う。

# バージョンを意識する

技術仕様は変化する。

バージョンによって挙動が異なる場合は対象を明示する。

例えば:

```text
Rspress v2 では……
```

```text
Spring Boot 3.x では……
```

```text
llama.cpp の 2026 年 8 月時点の実装では……
```

記事が将来読まれることを考え、「現在」「最近」だけで済ませない。

必要であれば具体的なバージョンや日付を書く。

# 実験結果と一般論を区別する

自分の環境で確認した結果を、一般仕様として扱わない。

例えば:

```text
RTX 4070 Ti SUPER 16 GB の環境では、この設定で生成に成功しました。
```

と、

```text
16 GB の GPU なら必ず動作します。
```

は異なる。

実験条件が結果に影響する場合は、主要な条件を書く。

# 数値には意味を持たせる

数値だけを提示しない。

例えば:

```text
14.8 token/s
```

と書くだけでなく、

```text
この環境では生成速度は約 14.8 token/s でした。
```

と意味を明確にする。

比較対象がある場合は、

```text
CPU オフロードなしでは約 20 token/s、CPU オフロードありでは約 12 token/s
```

のように並べると理解しやすい。

# 単位を書く

数値には必要な単位を付ける。

例:

- `16 GB`
- `300 秒`
- `14.8 token/s`
- `500 ms`
- `4 bit`

単位の異なる数値を比較しない。

# 情報量を段階的に増やす

最初から詳細な内部実装に入らない。

例えば次の順序を使う。

```text
概要
↓
基本的な仕組み
↓
具体例
↓
内部実装
↓
例外・制約
```

読者が途中まで読んでも主要な内容を理解できる構造にする。

# 見出しだけでも流れが分かるようにする

見出しは内容を表す具体的なものにする。

悪い例:

```markdown
## 概要

## 詳細

## その他
```

良い例:

```markdown
## CPU オフロードとは

## CPU オフロードで VRAM が減る理由

## CPU オフロードが遅くなる理由

## CPU オフロードが適しているケース
```

記事を見出しだけ流し読みしても、論理展開が分かるようにする。

# 見出しを細かくしすぎない

短い説明ごとに見出しを作らない。

複数の段落が一つの論点を説明している場合は、一つの節としてまとめる。

見出し階層が深くなりすぎる場合は、構成を再検討する。

原則として:

```text
#
##
###
```

程度を中心に使う。

# 箇条書きに逃げすぎない

箇条書きは、

- 特徴
- 条件
- 選択肢
- 比較項目
- 要点

などを並列に示すときに使う。

因果関係や仕組みの説明まで箇条書きだけで済ませない。

技術解説の中心は文章で構成する。

# 表は比較に使う

表は複数の対象を同じ軸で比較するときに有効。

例えば:

```markdown
| 方式 | VRAM 使用量 | 推論速度 | 特徴 |
| --- | --- | --- | --- |
| GPU のみ | 多い | 高速 | 十分な VRAM が必要 |
| CPU オフロード | 少ない | 低下する | 小さい GPU でも動作しやすい |
```

長い説明文を表に押し込まない。

表で概要を示し、重要な差は本文で説明する。

# 文章を短く切りすぎない

一文を短くすることだけを目的にしない。

文章同士の関係が分かる自然な段落を作る。

例えば:

```text
CPU オフロードを利用すると VRAM 使用量を削減できます。
これは、モデル全体を常時 GPU に保持する必要がなくなるためです。

一方で、推論中に CPU と GPU の間でデータ転送が発生します。
そのため、VRAM の節約と引き換えに推論速度が低下する場合があります。
```

のように、一つの論点を段落としてまとめる。

# 接続関係を明示する

必要に応じて次のような接続を使う。

- そのため
- 一方で
- つまり
- 例えば
- ただし
- これに対して
- この理由は

接続詞を機械的に付けるのではなく、論理関係が変わる場所で使う。

# 不要な前置きを避ける

次のような文章は必要がなければ省略する。

```text
今回は〜について見ていきます。
```

```text
それでは詳しく見ていきましょう。
```

```text
まず最初に〜
```

直接内容に入る。

# 読者への過剰な語りかけを避ける

技術ブログでも、必要以上に、

```text
皆さんも経験したことがあるのではないでしょうか？
```

```text
ぜひ試してみてください！
```

のような表現を挿入しない。

記事の雰囲気として必要な場合だけ使用する。

# 絵文字・文字装飾を使用しない

技術文書では、絵文字や装飾を目的とした文字表現を使用しない。

避けるもの:

- 絵文字
- 顔文字
- Unicode 記号を使った装飾
- 見出しへの絵文字付与
- 装飾目的の記号列
- 過剰な太字
- 過剰な斜体
- 強調を目的とした引用

例えば、次のような見出しは使用しない。

```text
🚀 高速化のポイント
✅ メリット
⚠️ 注意事項
✨ 便利な機能
```

通常の見出しを使用する。

```markdown
## 高速化のポイント

## メリット

## 注意事項

## 便利な機能
```

重要性は、まず文章の構造、語順、見出し、段落によって表現する。

太字や斜体などの文字装飾は、技術用語の定義など、明確な意味がある場合に限定する。

単に読者の注意を引くことを目的として文字装飾を使用しない。

文書の可読性を装飾に依存させず、次のような構造を使って情報を整理する。

- 見出し
- 段落
- 箇条書き
- コードブロック
- 表
- 図

# 誇張しない

次のような表現を安易に使わない。

- 革新的
- 圧倒的
- 爆速
- 最強
- 完璧
- 絶対
- 必須

技術的に説明できる具体的な性質を書く。

例えば:

```text
爆速になります
```

ではなく、

```text
CPU 実行と比較して生成速度が約 3 倍になりました
```

と書く。

# 「簡単」を安易に使わない

読者によって難易度は異なる。

```text
簡単にできます
```

ではなく、

```text
設定は `--cpu-offload` オプションを追加するだけです
```

のように具体的な作業量を書く。

# 技術名は正式表記を使う

製品名・プロジェクト名・技術名は正式表記を優先する。

例えば:

- Rspress
- PlantUML
- Spring Boot
- PowerShell
- TypeScript
- JavaScript
- GitHub
- llama.cpp

コード上の識別子は原文の表記を維持する。

# インラインコードを適切に使う

次のようなものにはバッククォートを使う。

- コマンド
- CLI オプション
- ファイル名
- ディレクトリ名
- 設定キー
- API パス
- クラス名
- メソッド名
- 環境変数
- ログ中の識別子

例えば:

```text
`--cpu-offload`
`rspress.config.ts`
`enable_model_cpu_offload()`
`/v1/chat/completions`
```

一般的な製品名や技術用語までバッククォートで囲まない。

# 引用したログやエラーを解説する

ログを貼るだけで終わらせない。

例えば:

```text
n_decoded = 203872
```

を掲載したなら、

```text
`n_decoded` はこのリクエストで生成されたトークン数を示しています。
この例では約 20 万トークン生成されているため、長時間実行の主要因として出力量を疑えます。
```

のように、そのログから何が読み取れるかを書く。

# サンプルと実データを区別する

架空の値を使用する場合は、実測値と誤解されないようにする。

実測値を掲載する場合は、必要に応じて環境条件を書く。

# 説明対象から外れる話を広げすぎない

関連技術だからという理由だけで、記事の本筋から離れた話を大量に追加しない。

本筋の理解に必要でない内容は、

- 短い補足にする
- 別節にする
- 別記事に分ける

ことを検討する。

# 一つの記事に一つの中心テーマを持たせる

記事を読み終えたとき、

「この記事は何を説明していたのか」

を一文で表せる状態を目指す。

複数の独立したテーマが混在する場合は、記事を分割することを検討する。

# 技術比較記事の構成

技術比較では、例えば次の構成を使える。

```text
比較する理由
↓
それぞれの概要
↓
共通する前提
↓
主要な違い
↓
比較軸ごとの分析
↓
用途別の向き・不向き
↓
まとめ
```

勝者を決めること自体を目的にしない。

# 仕組み解説記事の構成

仕組みを説明する場合は、例えば次の構成を使える。

```text
何が起きるのか
↓
前提知識
↓
全体像
↓
処理の流れ
↓
各要素の役割
↓
なぜその設計なのか
↓
制約や例外
↓
まとめ
```

# 問題分析記事の構成

障害や挙動を分析する場合は、例えば次の構成を使える。

```text
観測した現象
↓
環境・条件
↓
ログや計測結果
↓
分かったこと
↓
仮説
↓
検証
↓
原因
↓
得られた知見
```

「直し方」だけでなく、原因へ到達した論理を記事の中心にする。

# 検証記事の構成

技術を試した結果をまとめる場合は、例えば次の構成を使える。

```text
検証したいこと
↓
前提・環境
↓
検証方法
↓
結果
↓
結果の解釈
↓
制約
↓
結論
```

実験結果と、その結果から導いた解釈を分ける。

# まとめでは本文を繰り返さない

最後のまとめで記事全体を再掲しない。

主要な知見だけを短く整理する。

例えば:

```text
CPU オフロードは、VRAM 使用量を減らす代わりに CPU-GPU 間の転送コストを増やす仕組みです。

そのため、VRAM がボトルネックなら有効ですが、十分な VRAM がある環境では GPU のみで実行した方が高い性能を得やすくなります。
```

読者が持ち帰るべきポイントを明確にする。

# 完成前の確認

記事を完成させる前に確認する。

- 記事の中心テーマが明確か
- 想定読者に必要な前提知識が説明されているか
- 冒頭で何についての記事か分かるか
- 結論を不必要に隠していないか
- 「何が起きるか」だけでなく「なぜ起きるか」を説明しているか
- 因果関係の途中を飛ばしていないか
- 抽象的な説明に具体例があるか
- コード例の意味を本文で説明しているか
- 比較対象の比較軸が揃っているか
- メリットだけでなく制約やトレードオフを書いているか
- 事実、実験結果、推測、意見を区別しているか
- バージョン依存情報が明確か
- 見出しだけで記事の流れが分かるか
- 箇条書きや表に説明を押し込みすぎていないか
- 本筋から外れた内容が多すぎないか
- 絵文字や装飾目的の記号を使用していないか
- 太字や斜体を強調目的で多用していないか
- 最後に主要な知見が明確になっているか

# 最優先事項

文章の形式を整えることより、

「読者が技術の仕組みと、その理由を理解できるか」

を優先する。

単なる情報の羅列ではなく、情報同士の関係を説明する。
